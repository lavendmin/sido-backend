# 예약 확정 동시성 — Stay 행 잠금 도입/날짜 범위 잠금 제거 성능 비교

예약 확정 경로의 잠금 전략을 세 가지로 비교한다.

- **A** — 현 `develop`(`5f51f02`). Stay 행 잠금 없음. 날짜 범위 잠금(`StayAvailDate`·`ReservationDay` FOR UPDATE) 사용.
- **B** — 이 브랜치. Stay 행 잠금으로 확정·예약가능일 변경·숙소 비활성화 직렬화 + 날짜 범위 잠금 유지.
- **C** — B에서 날짜 범위 잠금만 제거(Stay 행 잠금 + 유니크 제약에 의존). 실험용 변형, 코드에는 미포함. **정합성 미충족으로 기각(아래 참조).**

## 환경·방법

- MySQL 8.0(REPEATABLE READ), Redis 7, Spring Boot 로컬 단일 머신, k6 v2.0.0.
- 100 VU 동시(`per-vu-iterations`, iterations=1). setup에서 user1 계정 1회 로그인, **전 VU 동일 쿠키 공유**(경합 재현 목적, 실제 사용자 100명이 아님).
- 확정 요청만 측정하는 커스텀 지표 `confirm_duration` 사용(setup의 생성 요청 제외).
- 각 버전·시나리오: 워밍업 1회 버리고 **5회 측정**, 중앙값 보고. 회차마다 예약·점유 삭제 + Redis flush로 초기화.
- 버전 전환은 앱 재기동이 필요해 **블록 설계**(A 전량 → B 전량 → C 전량). 회차별 A/B/C 교대 아님.
- 스크립트: `k6/reservation-confirm-distinct.js`(다른 날짜), `k6/reservation-confirm-seeded.js`(동일 날짜). 원자료: `raw/perf-*/`.

## 시나리오 1 — 동일 날짜 100건 동시 확정

동일 숙소·동일 2박 구간에 PENDING 100건(SQL 시드) → 100 VU 동시 확정. 1건 성공, 99건 409(예약 불가) 기대.

| 버전 | 5xx율 | 확정 성공(RESERVED) | confirm p90 중앙값 | confirm avg 중앙값 |
|---|---|---|---|---|
| A | 0% | 1 (이중예약 없음) | 0.38s | 0.23s |
| B | 0% | 1 | 0.58s | 0.34s |
| C | 0% | 1 | 0.43s | 0.27s |

세 버전 모두 이중예약 없이 1건만 확정. 동일 범위라 데드락 없이 직렬화. B가 A보다 약 50% 느린데, 추가 Stay 행 잠금과 (이제 중복인) 날짜 범위 잠금을 함께 잡기 때문. C는 날짜 범위 잠금을 빼 A에 근접.

## 시나리오 2 — 같은 숙소·서로 다른 날짜 100건 동시 확정

같은 숙소에 겹치지 않는 2박 구간 100개를 각 VU가 생성 후 동시 확정. **경합이 없으므로 100건 모두 성공해야 한다.**

지표는 **확정 요청 100건 기준**으로 읽어야 한다. `http_req_failed`는 로그인 1회 + 생성 100회 + 확정 100회(총 201요청)를 분모로 하므로 확정 실패율보다 낮게 나온다.

| 버전 | 확정 성공(RESERVED) 중앙값 | 확정 실패(=5xx) / 확정 100건 | 참고: http_req_failed(전체 201요청) | confirm p90 중앙값 |
|---|---|---|---|---|
| A | 약 71 / 100 | 약 29 / 100 (범위 19~38) | 약 14% | (실패 다수로 무의미) |
| B | 100 / 100 | 0 / 100 | 0% | 1.25s |
| C | 100 / 100 | 0 / 100 | 0% | 0.99s |

**핵심 발견 — A의 데드락.** A는 인접한 서로 다른 날짜 범위를 동시 확정할 때 `select ... from ReservationDay ... for update`에서 **데드락(InnoDB 1213, SQLState 40001)**이 발생한다(앱 로그 `Deadlock found when trying to get lock`, 실행당 수백 건 — `raw/perf/A-deadlock-excerpt.txt`). 그 결과 **확정 100건 중 약 29건이 5xx로 실패**하고 약 71건만 확정된다(전체 201요청 기준 `http_req_failed`는 약 14%). 인접한 범위의 `FOR UPDATE`가 잡는 gap lock 간 순환 대기가 유력한 원인이나, 보관된 발췌만으로 정확한 순환 관계까지 확정하지는 않았다(그 수준으로 단정하려면 InnoDB 데드락 상세 필요). 정렬 잠금(`ORDER BY`)은 겹치는 범위의 데드락은 막지만 이 경우는 막지 못한다.

B·C는 확정을 Stay 행 잠금으로 직렬화하므로 이 데드락이 사라진다(5xx 0%, 100건 전부 성공). C는 날짜 범위 잠금을 제거해 B보다 빠르다.

## C의 정합성 검증 — 부적합(채택 기각)

성능만 보면 C가 유리해 보였으나, **C는 정합성 재현 테스트(확정 ↔ 날짜 닫기)에서 실패**한다.
운영자가 확정 중인 날짜를 닫는 경합에서 확정과 날짜 닫기가 **둘 다 성공**해(`updateSucceeded=true, confirmSucceeded=true, avail=[], reserved=[...]`) 확정 점유일이 예약 가능일에서 사라졌다.

원인: 날짜 범위 `FOR UPDATE`(B)는 잠금뿐 아니라 **스냅샷을 우회한 최신 읽기** 역할도 했다. C처럼 잠금 없는 count 검사로 바꾸면, 확정 트랜잭션이 예약 행을 로드하는 시점에 잡힌 **과거 스냅샷**으로 가용성을 읽어, 운영자가 이미 커밋한 날짜 삭제를 보지 못하고 확정을 통과시킨다. Stay 행 잠금은 실행 순서를 직렬화하지만, 확정 쪽 가용성 조회가 스냅샷을 갱신하지 않으면 최신 상태를 보지 못한다.

성능 시나리오 2가 C에서 정상으로 보인 이유는 그 시나리오에 **날짜 삭제 경합이 없었기 때문**이다. 부하 테스트만으로는 이 결함을 드러내지 못했고, 결정적 재현 테스트가 잡아냈다.

→ **날짜 범위 잠금은 중복이 아니라 확정의 최신 읽기를 담당한다. B에서 유지한다. C는 기각.**

## 해석

- **A → B**: Stay 행 잠금은 확정을 숙소 단위로 직렬화한다. 동일 날짜 경합에서 지연이 약 50% 증가하지만, **같은 숙소·다른 날짜 동시 확정의 gap lock 데드락(A의 잠재 결함)을 제거**한다. A가 실패하던 부하에서 B는 전건 성공한다. B의 날짜 범위 잠금은 A처럼 데드락을 일으키지 않는데, Stay 행 잠금이 확정을 직렬화해 한 번에 하나만 날짜 범위 잠금을 잡기 때문이다.
- **B → C**: 성능은 C가 낫지만 정합성이 깨진다(위 참조). 채택하지 않는다.

## 한계

- 100 VU가 한 숙소에 몰리는 stress 조건. 동일 계정 쿠키 공유. 로컬 단일 머신. 회차 간 변동 있음(일부 회차에 GC 등으로 보이는 이상치). 내부 비교 수치이며 서비스 SLO가 아니다.
- 블록 설계라 시스템 상태 차이가 A/B/C에 체계적으로 섞일 수 있다. 다만 A의 데드락은 5xx·로그로 명확히 구분된다.

## 재현

```bash
docker compose up -d
# 스테이 22에 미래 240일 오픈(host1), 회차마다 예약 삭제 + redis flush 후:
k6 run k6/reservation-confirm-distinct.js   # 시나리오 2
RES_IDS=... k6 run k6/reservation-confirm-seeded.js  # 시나리오 1 (PENDING SQL 시드 필요)
```

두 스크립트는 계약을 threshold 로 강제한다: distinct 는 `confirm_success rate==1.0`(확정 요청 전용, 로그인·생성 제외 — 겹치지 않는 100건은 전부 성공해야 실행 성공), seeded 는 `confirm_ok count==1`(정확히 1건만 확정). 따라서 A처럼 일부가 실패하면 k6 실행이 실패로 끝난다.
